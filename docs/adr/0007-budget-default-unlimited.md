# ADR 0007: Budget defaults to unlimited, with metering

## Status

Status: accepted. Covers brief [§0](../self-improvement-software-factory-decision-brief.en.md) item 11 and §8.

## Context

The Owner asked for `unlimited` as the default budget. That must not be read as permission to remove other limits, nor as a promise about what a provider will charge.

## Decision

- Default `budget.mode: unlimited` means no monetary cap set by SISF. The ledger, cost display, alerts and cancel still operate.
- A fresh install shows the default and requires one Owner confirmation, together with setting `budget.alert_threshold` or explicitly declining. Until then the factory accepts intake but claims no tasks.
- Crossing the alert threshold notifies and does not stop unless the Owner chose `capped`.
- Timeouts, max attempts, concurrency, rate limits and quotas always apply. Roles and scopes never escalate on their own.
- In `capped` mode a reservation is made before a run starts. Unmeasured usage is shown as `unverified`; a provider without a hard limit is flagged.
- Usage whose provider reports tokens but no cost is recorded as reported, with no cost. When the reservation of a run with such usage is closed, the part of the reservation that the run's reported costs did not cover is charged as `unverified`; the reservation is the factory's own estimate of the run's worst case. The run's booked cost, and whether some of its usage stated none, are read from the run's rows in the ledger recorded since its reservation was made, never from the dispatcher's record of the run, which the agent zone can rewrite. A run with no row at all, or with a row that states no cost, with or without tokens, is charged its whole reservation as `unverified` less what its other rows booked, as is a run the dispatcher holds no record of: what it ran is unknown, and over-charging a run stopped before its first attempt is the safe side. This holds for a run the control zone stops as well: without a record of its own it is charged in full. A run with a row of negative cost is charged its whole reservation too, since only a hand that bypassed the store writes one; sums count a negative cost as 0. The record, and the QA judgments' own tally, can only raise the charge, for an attempt whose agent reported nothing and so left no row. A zone that may not read the ledger charges the whole reservation as `unverified` rather than trust the record. All reported costs stay `unverified`: no provider confirms them, so the store refuses usage booked as verified from every zone.
- The limit of this: the agent zone does the metering. The dispatcher books what its agents reported, so a compromised agent zone can under-report a run's cost down to one micro (a millionth of the ledger currency): a run whose rows each state some cost, however small, is taken at its word, and its reservation is then released for that. No code can tell an honest small cost from a false one while the agent zone meters itself; every cost an agent reports stays unverified. What is enforced is narrower and stated exactly. The store (`pkg/state/sqlstore/budget.go`): ledger rows are append-only; a usage row or reservation the agent zone writes through the store is dated by the store's own clock, and a usage row only against an existing reservation of the run and issue it names; rows dated before a reservation was made do not count at its close; a usage entry costs at most one million in the ledger currency (`core.MaxUsageCost`, booked at the bound above it; `cliagent` clamps an agent's reported cost to it too), and every sum of money is capped instead of overflowing and counts a negative cost as 0, so a close always ends. The gate adds a period's totals and an estimate saturating at the largest amount (`internal/budget/money_sum.go`), so totals near the store's cap fill the budget rather than wrap to a negative amount that lets any reservation fit. On PostgreSQL the database holds every zone role to the same rules over plain SQL (migration 13, `pkg/state/sqlstore/budget_row_time.go`, `row_policies.go`): it dates each reservation and usage row a zone role inserts by the server's clock, whatever the row says; it refuses usage booked as verified from every zone role; it refuses agent-role usage that does not name an existing reservation of the same factory, run and issue; and, with migration 12, refuses a negative cost on new rows (rows from before that migration are not rechecked). The table owner and roles that bypass row security are exempt, as the operator's own hand. On SQLite these rules hold only through the store. Migration 13 is marked backward compatible: the previous release books no verified usage and its agent books usage only against its own run's reservation, so it keeps working against the migrated database. Usage of a run that reserved nothing, as with an unlimited budget and a run estimate of 0, is not counted. `budget.get` warns when some unverified usage states no cost, with tokens or without, and its `unpriced` total counts those rows by the same rule a run's close applies (`core.Usage.CostUnreported`).

## Consequences

- The state store needs a transactional ledger and reservations.
- The guarantee level is reported openly rather than overstated.
