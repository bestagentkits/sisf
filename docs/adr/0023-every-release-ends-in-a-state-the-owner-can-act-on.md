# ADR 0023: Every release ends in a state the Owner can act on

## Status

Status: proposed. The Owner chose this direction after the trust review of the release lifecycle: a refused release leaves ReleaseCandidate, and an interrupted release is rolled back. After an independent review, the Owner's two lifecycle decisions (a release that cannot proceed leaves its state for Blocked with the reason; nothing waits for ever) were applied to Verified as well, and a unit's release was limited to the paths it consumes. This ADR records the decision for review before it is accepted.

## Context

A trust review of the release lifecycle found releases that stopped in a state nobody could act on:

- **Refused releases.** A release the supervisor refused before deploying anything left its issue in ReleaseCandidate for good. The refusal was recorded as a hold, and the Owner's retry was refused as final. A receipt or key that had expired since the hold was reported as a governance refusal, so the advice was to change the policy.
- **Failures after the rollout started.** A failure after the rollout began left the issue in Canary or Monitoring, or wrote a hold that named the wrong state. This covered a metrics read that failed, a promotion error, a lost lease, and a supervisor stopped mid-release. The LKG was not restored.
- **The synthetic suite.** A synthetic suite that could not be started, or whose run was cancelled, was judged as a failed check.
- **Restarts.** After a restart, the local deploy backend lost track of the application process it had started, and the next start of the LKG collided with it on the slot's port.
- **Reservation closes.** A budget reservation close that could never succeed was retried on every pass, for ever.

## Decision

- **A refused release blocks its issue.** A new lifecycle edge, ReleaseCandidate → Blocked on event `release_refused`, is unguarded like the other edges into Blocked (`pkg/core/statemachine/table.go`). The issue is blocked with cause `release_refused`, and the stop record keeps the refusal's code (`cmd/supervisor/handoff/run_stop.go`). The issue's summary names the code's meaning. `EXPIRED` says the receipt or the signing key expired. `APPROVAL_REQUIRED` says the change touches the trusted surface or a unit outside `release.units`. A verification failure says the candidate did not verify. The candidate's pull request is noted as refused, never as rolled back. Only a refusal that judged the candidate or the request blocks the issue: the codes `APPROVAL_REQUIRED`, `EXPIRED`, `SIGNATURE_INVALID`, `TAMPERED`, `GUARD_FAILED`, `INVALID_ARGUMENT`, `PERMISSION_DENIED`, `NOT_FOUND` and `REPLAYED`. A check that failed for any other reason, or whose context ended, judged nothing; the release does not begin and is tried again on the next pass. A candidate whose program is byte for byte the LKG's, as one that changes only tests or documentation, is refused with `ALREADY_EXISTS` after it verified, instead of being held. The lifecycle has no truthful way from ReleaseCandidate to Verified without a rollout, and a hold would only be resumed and held again. The summary says that the candidate builds the program already serving and that its pull request is merged by hand.
- **The supervisor is the control zone.** The task asked for the edge to be the supervisor zone's alone. The store has three zones (application, agent, control), and the supervisor writes as the control zone, so the edge is admitted to the control zone only. It is listed in `controlEvents` (`pkg/state/sqlstore/zone_ownership.go`) and in the PostgreSQL record trigger and row policies generated from those rules. Like every step from Claimed through Monitoring, the step needs the issue lease and the run the record names. The agent zone's role cannot take it, and the application zone writes no step.
- **Migration 10** (`0010_release_refusal_and_lease_steps`, backward compatible) installs the new step on PostgreSQL and a trigger on `leases`, `sisf_lease_step` (`pkg/state/sqlstore/lease_step_trigger.go`). The trigger holds every change of a lease to one of the writes the lease API makes:
  - insert at token 1;
  - take over by raising the token by exactly one under a named holder;
  - renew by the same holder;
  - give up by keeping the token.

  A zone role can no longer raise a token with plain SQL to meet the record trigger's rule without taking the lease. The trigger does not judge expiry, because the database does not share the store's clock. It does not bind holder names to zones either, because the lease API does not. On SQLite the migration is a no-op.
- **Any failure after the rollout starts restores the LKG and blocks the issue.** Restores and blocks are written in `internal/supervisor/release/restore_and_recovery_report.go`. The cause names what happened:
  - `rolled_back`: the rollback rules judged the release unhealthy.
  - `release_unjudged`: the release could not be observed or measured, or its synthetic suite could not be run.
  - `release_interrupted`: the supervisor stopped, an emergency stop took effect, a promotion failed, or the step could not be written.

  The lease is renewed, or taken back as the same holder, before the backend rolls back. A restore that rolled back but could not block the issue is finished on the next pass. A hold is written only for a release still in ReleaseCandidate.
- **An unwatched release is recovered at startup and on every pass.** A record in Canary, Monitoring or RolledBack is recovered when no release of this process drives it. Recovery runs after the LKG adoption, so the local backend runs the LKG again before anything is rolled back to it (`internal/supervisor/release/release_recovery.go`, `cmd/supervisor/stages/release_stage.go`, `cmd/supervisor/lifecycle_loop.go`). Recovery restores the LKG through the deploy backend, records RolledBack and then Blocked with cause `release_interrupted`, and writes the recovery report. A per-issue registry in the pipeline lets one goroutine drive an issue at a time. Recovery takes the issue lease, and the version check of each step means that one of two concurrent recoveries writes the steps and the other finds the record already moved. Within one process, the LKG is restored once.
- **The LKG names what serves.** The last known good release of a unit is recorded only for a release observed serving that unit, healthy, at that moment (`internal/supervisor/release/verified_release_lkg.go`). Releases of a unit are ordered by the order the store wrote their Verified steps in, never by when an entry was written, and by a clock only between two releases an earlier build verified before steps were numbered. In its transaction each Verified step takes the next number of a counter (`verified-sequence` in the `release` namespace), above the number of the unit's LKG on the trust volume and of every release still Verified, and keeps it in `finish-due/<run>` (`sequence`); the LKG entry keeps it as `verified_sequence` (`internal/supervisor/release/verified_sequence.go`). An entry an earlier build wrote may still hold `verified_step_at`; it is read only to order that entry against a release an earlier build left Verified, neither numbered, by when their Verified steps were written (`verifiedLater`). A later install is recognised by identity, not by time: the finish-due keeps when the root-signed release manifest record in force at the Verified step was recorded (`install`), and an LKG the manifest pins with any other record is a later install. The LKG entry also keeps the commit its release was built from (`commit`, from the verified receipt). A verified release is judged on its QA evidence as of its Verified step: the receipt and the delegated keys that signed it are checked by a verifier pinned at that instant (`Config.VerifierAt`, `cmd/supervisor/delegated_keys.go`), so evidence that merely expired since does not hold the release for good. Only expiry is judged as of that instant: a key revoked since is refused. The supervisor's own signature of the build is made again on every pass and checked as of now.
- **A verified release is finished, superseded, or blocked.** The finish writes the Verified step and, in the same transaction, a `finish-due/<run>` record of what the release still owes, and only then records the LKG (`internal/supervisor/release/verify_publish_and_close.go`, `verified_finish_due.go`). A Verified step that cannot be written leaves the LKG as it was, and the release is restored to it and blocked as interrupted. For each verified release the finish then decides one of three things:
  - **Recorded:** the release serves, healthy, its evidence verifies as of its Verified step, and no later release superseded it. It becomes the LKG, is published and is landed.
  - **Superseded:** another release of the unit was verified after it, the LKG names a release verified after it, or a later root-signed install pins the LKG. The unit of another Verified release is the one the build record of its candidate commit names (`build/<commit>`, reached through `candidate/<run>/<attempt>` and checked against the digest the record names), never what its `finish-due/` says (`unit_of_verified_release.go`). It is closed without the LKG and without a publication. Its landing is handed over marked as superseded (`LandRequest.Superseded`), and the factory does not merge it: the Lander leaves its pull request to the Owner, unless the Owner already merged it, which stands. Every candidate is built from the default branch, and the factory merges only after the LKG step, so a superseded release that was not merged is never an ancestor of what serves; merging it would put a change on the default branch that no release observed.
  - **Unjudged:** the running system shows another release serving the unit, healthy, or the release's evidence does not verify even as of its Verified step, and nothing superseded it. The issue is blocked (below). A running system that does not answer at all is an outage that clears: the release waits and is judged once it answers.
  - **Unseen:** the running system shows neither the release serving, healthy, nor another release in its place: the probe failed, timed out or found no process (no digest), or the release answers its health check as down. That judges nothing. The release is observed again on every pass for as long as a release is watched before it is verified (`Monitor.Window` times the observation windows), counted by this process from the first pass that did not see it, and started again by a pass that sees it serving, healthy, even when a later step of that pass fails, and by a pass an emergency stop skips; it is never kept in a document. Once that wait has passed, the LKG is restored and the issue blocked as unjudged, the block saying why (`verified_release_unseen.go`).

  The publication, the landing and the closing step follow, and each is safe to repeat:
  - the publication is recorded as done in that record, and the Publisher's pull request is found again by its branch rather than opened twice (`cmd/supervisor/stages/publication_pull_requests.go`);
  - the Lander decides a landing once;
  - the closing step deletes the record.

  Every pass resumes every Verified record (`FinishVerified`), whether its publication, its landing, the write of its LKG or an emergency stop held it, and whether the stop has been lifted since. A record an earlier build left Verified, with only `landing-due/<run>` or nothing recorded as due, is finished the same way. What finishing waits on is written to the candidate's pull request record as a pending landing with its reason, the way a landing that waits is shown in the issue's progress, and is logged once per change. A release waits in Verified only on an outage that clears: the store, the trust volume, the deploy backend's answer, the publication, GitHub, the supervisor's own signing key, or an emergency stop. Before the LKG is adopted at startup, a Verified release that the LKG does not yet name is recorded as the LKG when, and only when, the running system serves it, healthy; one that is unseen is observed again, every five seconds, for the same wait first, all of them together, so startup waits that time once however many there are, so adoption does not start the LKG over a release that was only slow to answer. Startup writes no step, and a release it cannot record is judged on the next pass. A release left in Monitoring that an earlier build already recorded as the LKG is verified by the recovery from the running system instead of being restored to itself; one that is no longer healthy has nothing to be restored to and is blocked as `release_unjudged`, saying that nothing was restored. Under an emergency stop that verification waits until the stop is lifted and is reported once, because verifying is a step forward; a rollback is not held.
- **A verified release that cannot be judged blocks its issue.** A new lifecycle edge, Verified → Blocked on event `verified_release_unjudged`, cause `release_unjudged`, is taken only for an unjudged release, never for a superseded one or one waiting on an outage that clears (`pkg/core/statemachine/table.go`, `internal/supervisor/release/verified_release_lkg.go`). Unless another release is observed serving the unit, healthy, and when another release is the LKG, the unit is switched back to the LKG first, whether the release serves with evidence that does not verify or the running system could not show what serves; a switch that fails leaves the issue Verified and is tried again on every pass. When there is no other release to switch back to, the issue is blocked and the block says that nothing was restored. In the step's transaction the recovery report is written and what the release owed (`finish-due/`, `landing-due/`) is dropped, so it is not published and its pull request stays open and unmerged; the Owner's summary says so (`cmd/supervisor/handoff/run_stop.go`). The Owner's retry returns the issue to Ready. Like the refusal edge, the step is the control zone's alone (`controlEvents` in `pkg/state/sqlstore/zone_ownership.go`), and **migration 11** (`0011_verified_release_unjudged_step`, backward compatible) rebuilds the PostgreSQL record trigger and row policies from the table to admit it; on SQLite it is a no-op.
- **A rollback never waits for the issue lease.** When recovery cannot take the lease of a release left in Canary, Monitoring or RolledBack, it restores the LKG through the backend anyway. This happens when an emergency stop of an earlier build holds the lease, or when a role took it over and keeps renewing it. The LKG is switched to once per release and process. The stage reports the wait once per change, and the report names the holder: a refused lease now carries its holder in the error details (`pkg/state/sqlstore/leases.go`). The RolledBack and Blocked steps are written by the first recovery that can take the lease. The switch made without the lease is audited (`release.rollback`, `without_lease`), and the recovery report of the later block names the release the switch actually left serving, as observed after it. The emergency stop no longer holds the leases of issues in Canary, Monitoring or RolledBack (`internal/supervisor/killswitch/hold_claims_and_stop_runs.go`). Under a stop the supervisor moves those issues only back to the LKG, because the pipeline checks the stop before every forward step. The stop freezes forward progress and never blocks a rollback.
- **A RolledBack record keeps its cause.** The restore writes why it rolled the release back (`restore-cause/<run>`) in the transaction of the RolledBack step. A recovery that later blocks the issue reuses that cause and reason, so a release judged unhealthy is blocked as `rolled_back`, not as `release_interrupted`. Only a RolledBack record left by an earlier build, which kept no cause, is blocked as interrupted.
- **The Owner's retry returns these blocks to Ready.** The retry guard admits `release_refused`, `release_interrupted` and `release_unjudged` on the Owner's authorization alone, as it does `rolled_back` (`pkg/core/statemachine/retry_guard.go`). A rollback block written before its stop record existed is judged from its recovery report (`cmd/factoryd/wiring/owner_retry.go`). A second retry of the same block is refused with `INVALID_TRANSITION`, and a non-Owner is refused. The retry of a held build or release now reports a hold record it cannot read, such as `TAMPERED`, instead of going on as if nothing were held.
- **The synthetic suite tells a run that judged nothing from a failed check.** A program that cannot be started, or a run whose caller stopped it, is an error. Only a run that outlasts its own time limit is a failed run (`cmd/supervisor/synthetic_program.go`). The supervisor refuses to start when `--synthetic-program` is missing, not a regular file, or not executable. Before a low-traffic release deploys anything, the supervisor asks the suite whether it can run, and holds the release when it cannot. During the rollout, a suite error restores the LKG as `release_unjudged`.
- **The local backend records its processes and finds them again.** For each slot it writes the pid, the process start time (on Linux the boot id and the clock ticks from boot in `/proc`, which a step of the clock does not change; elsewhere `ps`'s start, to the second; read by `internal/processstart`, shared with the installer), the command line, the port and the release to `<trust>/local-slots/<slot>.json` (`adapters/deploy/local/slot_records.go`). When the backend is built after a restart it rebuilds its slots from those records, before the startup records any LKG: a recorded process whose pid still has the recorded start time, read the way the record was written, is the slot's process again, as the release the record names, on the port the configuration gives the slot. A supervisor that stopped between a Verified step and its LKG thus observes the release it started and records it, instead of stopping it and starting the release before it. A record whose process is gone, or whose pid now names another process, is dropped without a signal; one whose process runs on another port than its slot's is stopped, once its pid is shown to name it, and dropped. A process found again is stopped when its slot is staged over or rolled back from, and when the supervisor stops (`Close`, both slots together), because it is in the process group of the supervisor that started it, which no signal to the new supervisor's group reaches. Each signal is sent only after the pid is shown to name the recorded process still; the start time survives the `exec` by which the installed launcher becomes the release's program, and the command line is kept for the log only. No process is matched by name or pattern. A process that ignores `SIGTERM` is killed after five seconds.
- **A reservation close that can never succeed is abandoned once.** A close that fails with `NOT_FOUND`, `TAMPERED` or `INVALID_ARGUMENT` is counted. After five such failures, the run's close-due entry is replaced by `close-abandoned/<run>`, which holds the code and the reason, and the pass reports it once. A close that fails for a passing reason is retried on every pass and never counted (`cmd/supervisor/stages/run_close_due.go`).
- **The protected Go packages are the trusted binaries' dependency closure.** The Go part of `DefaultProtectedPaths` is no longer kept by hand. `go generate ./internal/supervisor/release/` writes every directory of this module that `./cmd/supervisor`, `./cmd/sisf` or `./cmd/factoryd` links, on Linux and macOS, amd64 and arm64, with and without cgo, to `trusted_go_package_dirs_generated.go` (`internal/supervisor/trustedclosure`). There is no separate QA evaluator binary: the evaluator runs inside the supervisor. Each directory covers everything below it. A test computes the closure again with `go list -deps` and fails when the checked-in list is stale. The command line and the control unit are trusted binaries too: the installer, sign-in, roles and approvals, and the dashboard's templates and scripts, which show the Owner what an approval is for, are all in their closure, so `ui/`, `cmd/factoryd/`, `internal/control/`, `internal/install/` and `cmd/sisf/` are protected without a hand-kept entry. The hand-kept entries stay for what is not a linked Go package: the Dockerfiles, `templates/`, `.sisf/`, the foundation files, `docs/adr/`, the synthetic suite and `.github/`. `internal/supplychain/`, `internal/redact/`, `build/runner.Dockerfile` and `build/qa-runner.Dockerfile` are among them. A candidate that touches any of these paths is refused with `APPROVAL_REQUIRED` and its issue is blocked before anything is deployed. The edge (`cmd/edge/`, `build/edge.Dockerfile`) and `go.mod` and `go.sum` are protected by hand too: the edge decides which release receives traffic, and a changed dependency version changes what every trusted binary links without touching one of its directories.
- **The supervisor links no part of the control unit.** It reads the simulation profile, the GitHub settings and the store directory through `internal/manifestsettings`, never through `cmd/factoryd`, and a test fails if the supervisor's own closure contains `cmd/factoryd/`, `ui/`, `internal/control/`, `internal/mcp/` or `internal/oauthas/`. The control unit's code is protected all the same, through the closure of `./cmd/factoryd`.
- **Identity and access code is protected through the closure.** `internal/auth/`, `internal/rbac/`, `internal/oauthas/` and `pkg/identity/` decide who the Owner is and who may approve; the command line and the control unit link them, so the generated closure names them and the earlier hand-kept list of them is removed. Nothing in Go is hand-kept that the generator can derive.
- **A unit releases only what it consumes; everything else needs the Owner.** Each self-publishable unit has an allowlist of the paths it consumes, compared case-folded (`internal/supervisor/release/unit_inputs.go`):
  - `app`: the directories of this module's packages that `./examples/hello-app` links, from `go list -deps`, each covering only its own files, not its subdirectories. `go generate ./internal/supervisor/release/` writes the directories to `app_unit_package_dirs_generated.go`, and a test fails when the list is stale. `go.mod`, `go.sum` and `go.work*` are never built-in inputs, wherever they are: a changed dependency changes every binary of the module. `build/hello-app.Dockerfile` is not an input either: it decides how the application is built, which observing one release cannot vouch for.
  - Any other unit, `control` included, has no built-in input and consumes nothing. Everything under `ui/` is linked by the command line and the control unit and is protected; a page of the control unit outside it is an input of `control` only when the Owner declares it.

  These are the built-in inputs. The Owner may declare a unit's inputs instead in the installed manifest's `release.unit_inputs`, which maps a unit named in `release.units` to path patterns relative to the repository root (`pkg/manifest/unit_inputs.go`). It exists because a factory may work on a repository that is not laid out like this one: the sandbox repository keeps its application's `app.go` at its root, which no built-in input covers.
  - **Matching.** Patterns are case-folded and matched with `path.Match` against the whole path, so `*` never crosses a `/`. A name without a wildcard matches that one file. Decoding refuses an empty pattern, `**`, a leading `/`, `..` or `.` segments, a backslash, and a pattern whose every segment is only wildcards (`*`, `*/*`), each with the reason.
  - **Replacement.** An entry replaces the unit's built-in inputs entirely; a unit without an entry keeps them. Go-toolchain files may be inputs of `app`. Files the Go toolchain reads (Go, assembly, C, `go.mod`, `go.sum`, `go.work*` and the others `go build` reads) are never inputs of any other unit, declared or not: such a unit is observed as a program that is not built from them.
  - **Conformance proves what it can.** `sisf conformance` and `sisf up` refuse a pattern that can match a protected path (`release.unit_inputs_protected`), the dashboard's templates and static files under `ui/` included, a pattern of any unit but `app` that can match a file the Go toolchain reads (`release.unit_inputs_go_code`), and a pattern that can match a path another unit consumes, declared or built in (`release.unit_inputs_overlap`). Each finding names a path both sides match (`internal/supervisor/release/unit_input_conflicts.go`).
  - **Release time refuses the rest.** What conformance cannot prove is still refused when the candidate is released: a path that is both a declared input and protected is refused by the protected layer, which stays on top whoever declared the input, and a path two units consume is the input of no single unit, so its candidate needs the Owner's approval.
  - **Only the installed manifest declares inputs.** The supervisor reads `release.unit_inputs` from the manifest it was started with (`--factory-manifest`), the same way it reads `release.units`, and never from the repository a candidate changes. `.sisf/factory.yaml` in the repository is protected, so a candidate that edits it to widen its own inputs is refused for the Owner, and the installed inputs stay as they were. The installed manifest is written by `sisf` in the install directory, readable by all and writable by the Owner, and mounted read-only into the containers in Docker mode. It is Owner-declared, not signed: the root-signed release manifest pins digests, not this setting, so whoever can write the install directory can widen a unit's inputs, as they can already change every other setting there.

  A candidate that changes any path outside the allowlist of the unit it releases is refused with `APPROVAL_REQUIRED` before anything is deployed, and the refusal names the first paths and says they need the Owner's approval. Observing a unit cannot vouch for a change it does not run. The check runs in governance after the protected paths, which stay as a second refusal layer, and again before the factory merges (`mayNotMerge` in `cmd/supervisor/stages/candidate_landing.go`). The paths judged at both points are listed again from GitHub's comparison of the policy commit the verified QA receipt names with the candidate commit it names (`changed_paths_from_github.go`); the list stored with the candidate, a document of the control zone, can only add paths to it, which also keeps the old side of a rename GitHub lists by its new name only. A comparison GitHub cuts short or refuses is refused for the Owner like a listing marked incomplete; one GitHub cannot answer now is a wait. The merge also leaves a candidate whose pull request head is not the commit the receipt names to the Owner. A path that is not its own clean form, one that trimming or `path.Clean` would change, is refused: the builder commits a path exactly as it is spelled. The router (`UnitRouter` in `cmd/supervisor/stages/builder.go`) derives the unit of a change from the same inputs, declared or built in; a change that spans two units is refused, and a change of no unit's inputs is built as `app` only so that QA judges it and its pull request opens, and its release is then refused for the Owner. The earlier default that routed everything else to `app`, and the generated list of the control unit's Go packages, are removed. A test classifies every path `git ls-files` lists as the input of exactly one unit or as needing approval.
- **A candidate's base must hold its unit's LKG release.** After the receipt and the build verify, a candidate is refused with `APPROVAL_REQUIRED` before anything is deployed when the policy commit its receipt names, the base it was built and judged on, does not contain the commit of the LKG release of its unit (`base_contains_lkg.go`). Releasing it would serve, and merge, the unit without the change that release made, and every later release built on that base would drop it too. Containment is GitHub's three-dot comparison of the base with that commit, which lists nothing exactly when the base contains it. A comparison cut short or refused, a commit GitHub does not know included, cannot show it and is refused the same way; one GitHub cannot answer now is a wait. An LKG the install pins names no commit, so the first release of a unit on a fresh install, and a candidate rolled back, which leaves the LKG as it was, are not affected. The reason names the base, the commit and the run of the LKG release. The commit candidates are built on, and its move after the factory's own merge, are decided in [ADR 0026](0026-the-commit-to-build-on-follows-main.md), which also stops such a candidate right after its build, before QA; this refusal stays as a second check.
- **Unchanged:** the QA pass mark, the hard gates, `SelectImageBuilder`'s refusal of an untrusted build without an isolating backend, the supervisor boundary, the Docker filter, and the supervisor-only merge.

## Consequences

- No release waits in ReleaseCandidate, Canary or Monitoring without a supervisor driving it. Every refusal and every undo ends in Blocked with a cause, a public summary and the Owner's way out. A retry spends agent budget on a new run, and the refused candidate itself is never tried again.
- An interrupted release is rolled back even when it might have been healthy. The summary says that nothing is known about its health.
- **Recovery across processes.** The registry and the lease narrow the race between two supervisor processes of one factory, but do not close it:
  - the lease re-grants itself to the same holder name, which is what makes a restarted supervisor take over at once;
  - a second process with the same name could therefore also call the backend's Rollback before the version check refuses its steps.

  One supervisor per factory is the supported setup. A rollback to the LKG is idempotent on both backends.
- The leases trigger stops a zone role from forging a token. It does not stop a role from taking over a lease that is still live, because the trigger does not judge expiry.
- The slot records are on the trust volume. In Standalone mode the agent's operating-system user can write that volume, so it could forge a record. The start time check means a forged record can only name a live process whose start time it gives exactly, which that user could signal anyway.
- A process found again after a restart is managed as one the backend started, with two differences. Its critical log lines are no longer counted, so a rollback rule on them does not fire for it. Its standard error is a pipe whose reader was the supervisor that started it: a Go program writes to it once more and is ended by `SIGPIPE` (the hello application writes there only for an injected fault). Such a release then goes unseen, and after the wait the LKG is restored and the issue blocked. A backend that was never given a state directory keeps nothing on disk, as before.
- An abandoned reservation stays held until a person settles it. The record and the one-time report say which one.
- **Default-deny inputs.** A change to documentation, tests, the Makefile, `go.mod`, a vendored file or any other path no unit consumes is never merged by the factory: QA judges it and opens its pull request, and the issue is blocked for the Owner to merge by hand. A repository whose application is laid out differently needs its inputs declared in `release.unit_inputs`; until the Owner declares them, its candidates are refused the same way. The smoke install declares the sandbox repository's `app` inputs as `*.go` at its root.
- **Startup waits for an unseen release.** A Verified release whose LKG write was lost is recorded at startup when its process still serves it. One the running system does not show serving holds startup for up to the observation windows before the LKG is adopted; the application is served by whatever the edge points at meanwhile, as it would be during the same wait on a later pass. A backend that does not answer at startup records nothing and writes no step; the error is logged with the pass and startup goes on.
- **One self-published release per unit and baseline.** Superseded by [ADR 0026](0026-the-commit-to-build-on-follows-main.md): the supervisor moves the commit candidates are built on after its own merge while the approved foundation content is unchanged, so releases of a unit follow one another.
- **Upgrading with a release unfinished.** A `finish-due/` or LKG entry an earlier build wrote has no sequence and no install. It is ordered before every numbered release and is never taken as superseded by an install. Two such entries are ordered by when their Verified steps were written, so a release left Verified across the upgrade is superseded by a later one an earlier build verified; otherwise it is judged by what the running system shows: if another release serves, it is blocked rather than closed as superseded.
- **Keys seen since the start.** The pinned verifier trusts only the delegations the supervisor has loaded since it started. A receipt signed by a QA key that was rotated away before a restart does not verify, and its release is blocked as `release_unjudged` rather than finished.
- **The control zone writes the release documents.** The `release` namespace is not listed in the store's namespace rules, so it falls to the control zone, which factoryd shares with the supervisor. `finish-due/` is read only by `FinishVerified`, which acts only for a record Verified with the same run and release, so a forged entry for any other run does nothing, and the unit of another release is read from its build record rather than from it. Its `sequence` and `install` and the `verified-sequence` counter can be forged too: the floors keep a deleted or lowered counter from ordering a new release before the LKG or a release still Verified, but a raised or lowered `sequence` can still make a release be taken as superseded, closed unpublished with the LKG left on the release before it, or an earlier one taken as later. A forged `restore-cause/` can choose the cause a later block is written with. Moving these documents to a namespace only the supervisor's role can write is left to a change of the store rules.

## Alternatives considered

- **Keep a refused release in ReleaseCandidate with a final hold.** This was the previous behaviour. Rejected by the Owner, because the issue could never move again without hand repair of the store.
- **Retry a refused release in place.** Rejected. An expired receipt or a governance refusal does not change by waiting, and resuming the same candidate would sidestep the requirement for a new QA judgment.
- **Let a restarted supervisor resume watching an unwatched release.** Rejected. The watch window, its samples and the synthetic runs of the interrupted release are lost, so the release cannot be judged on evidence. Restoring the LKG is the safe direction.
- **Find stale processes by port or program name.** Rejected. A pattern or port match could stop a process the supervisor did not start.
- **Stop every recorded process at startup, as before.** Rejected. It stopped the release a supervisor verified just before it stopped, and the startup then put the release before it back and blocked the verified one.
- **Order releases by the journal's sequence.** The transitions journal has no sequence column; adding one needs a migration on both stores. The counter written in the Verified step's own transaction orders the same steps without one.
- **Advance the trust baseline when the factory merges its own release.** Not done for the policy revision, which stays the Owner's. [ADR 0026](0026-the-commit-to-build-on-follows-main.md) moves a separate commit to build on instead.
