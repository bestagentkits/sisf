# Operations

How to run and inspect an installed factory. Behaviour is owned by the code; this page says where to look. Commands and flags: `sisf help <command>` and the [CLI reference](cli-reference.md). Procedures: [installing](install.md), [maintenance](maintenance.md) (upgrade, backup, restore), [policy, approvals and budget](policy-and-approvals.md), [Why is my issue stuck?](stuck-issues.md), [troubleshooting](troubleshooting.md).

## Lifecycle

| Task | Command |
|---|---|
| Start (builds, signs, checks isolation, starts all zones) | `sisf up` |
| Stop and keep everything | `sisf stop` |
| Restart every unit | `sisf restart` (Standalone also restarts on SIGHUP) |
| Stop and remove what the run created | `sisf down` (`-v` removes data too) |
| Health of the install | `sisf doctor` |

All of these take `--dir`; the default is `$SISF_HOME`, else `~/.sisf/factory`. Run `sisf doctor` after every start and before relying on rollback: it checks that a last known good release is recorded.

A Standalone `sisf up` passes its run lock (`<dir>/run/sisf.lock`) to every unit it starts, and each unit records its process under `<dir>/run/units/`. The install therefore counts as running while any unit lives, also after the `sisf up` that started it was killed. `sisf stop` and `sisf down` then stop those units, each shown to be the recorded process by its pid and start time first. `sisf up` and `sisf restart` refuse while they run and say to run `sisf stop --dir DIR` first. A unit marks the inherited lock close-on-exec, so the agents, builds and application it starts cannot hold the lock after it. If the lock is held by no `sisf up` of this install and no unit it recorded, the refusal says so and signals nothing: [troubleshooting](troubleshooting.md#installing-and-starting). On Linux the units of a killed `sisf up` are told to stop (SIGTERM) when it dies; elsewhere they keep running and hold the install as running until `sisf stop`. A process's start time, which tells a recorded unit from a later process that got its pid, is read from `/proc` on Linux, with no dependency on `ps` or the time zone, and from `ps` elsewhere (`internal/install/process_identity.go`). The code is `internal/install/run_lock.go` and `run_unit_records.go`.

After a unit was killed rather than stopped, an agent CLI it started can outlive it in its own process group without holding the run lock, so `sisf down -v` may delete a workspace under that agent. After a crash, check that no agent process remains before removing volumes.

## Inspecting the factory

- `sisf status` shows the overview. `sisf issues` lists tracked issues.
- `sisf runs inspect <issue|run-id>` shows the record; `sisf runs explain <issue|run-id>` says why a run is stopped or blocked.
- `sisf approvals list` and `sisf approvals get <id>` show Owner approvals. A decision is bound to the approval's nonce, subject digest and policy revision, and is made on the dashboard at `/approvals/<id>`: `sisf approvals decide <id>` can only preview one with `--dry-run` and otherwise answers `STEP_UP_REQUIRED` ([deciding an approval](policy-and-approvals.md#deciding-an-approval)).
- `sisf call <action>` calls any action over REST (the catalogue is in [`api/openapi.yaml`](../../api/openapi.yaml)). Add `--dry-run` to preview.

Every surface runs through one action service and one action registry (`internal/actions`, registered by `internal/actions/actionsets`), so none holds extra power. The control server (`internal/control/surfaces.go`) mounts them all on one port:

| Path | Surface | Caller proves itself with |
|---|---|---|
| `/api/v1/` | REST, and the CLI through it | a personal access token, or a dashboard session plus its CSRF token |
| `/mcp` | remote MCP | an OAuth access token issued by the factory's own authorization server |
| `/webmcp/actions.json` | the WebMCP tool list `ui/static/webmcp.js` reads | a dashboard session |
| `/.well-known/oauth-*`, `/oauth/` | the OAuth authorization server (`internal/oauthas`) | none, or the dashboard session on consent |
| `/auth/` | sign-in callback, step-up confirmation, sign-out, the session and personal access tokens | the identity provider, then the session |
| `/` | the dashboard: its pages, `/signin`, `/logout` and the action forms under `/actions/` | a session cookie; form posts also need the CSRF token |

Parity across the five surfaces is proven by `tests/acceptance/five_surface_parity_test.go`; see the [acceptance matrix](../acceptance-matrix.md).

## Progress on the issue and the candidate's pull request

- Each claimed issue carries one factory comment, marked `<!-- sisf:progress -->`, edited in place at every checkpoint of a run in flight: the claim, each failed coding attempt, each QA verdict (score, pass mark, failed hard gates), a QA hold, the candidate's pull request, the release steps, a rollback, the merge or why there was none, and the close. It is rendered from the factory's records only, redacted, and written only when it changed (`cmd/factoryd/wiring/progress_projection.go`, `progress_render.go`).
- A run that is rolled back is followed until it reaches Blocked, so the comment shows the recovery. An issue whose run ended before it had a progress comment is not given one. A comment that cannot be written is tried again after a pause that doubles up to an hour. A Closed issue is closed on GitHub only after its comment shows the end: an outage, a 5xx or a rate limit holds the close until GitHub answers again, however long that takes. Only a comment GitHub refuses for good (a locked issue, or a 403, 404, 410 or 422 answer) is given up, after three such refusals counted from the run's end, and the issue then closes without it; failures while the run was in flight do not count.
- When QA passes a candidate, the supervisor opens one pull request from `sisf/<factory>/<run>-<attempt>` to `main`, saying `Refs #N` so the merge does not close the issue (`cmd/supervisor/stages/candidate_pull_request.go`). `sisf runs inspect` shows it as `pull_request` with its state: `open`, `pending` (merging), `merged`, `left_for_owner`, `rolled_back` or `refused`.
- After the release of that candidate is verified, the supervisor merges the pull request at the candidate commit, then the issue closes ([ADR 0021](../adr/0021-candidate-lands-by-supervisor-merge.md), `cmd/supervisor/stages/candidate_landing.go`). It does not merge a pull request it did not open itself (one someone else opened on the candidate branch), nor a candidate that changes a foundation or policy file, whose branch moved, whose policy pin no longer holds, or whose release was rolled back; the pull request is then left open with a note, `sisf runs explain` gives the reason, and the progress comment says the change is **not** merged. Merge or close those by hand.
- When GitHub cannot be reached for the merge, or an emergency stop is in force when the merge is due, the issue stays in Verified with its landing recorded as due, and the merge is tried again on a later round (after the stop is lifted, and also after a restart); it is never merged twice. The record that the landing is due is deleted when the issue closes. When GitHub refuses the supervisor's token (401), the merge is not decided: the candidate's record and the progress comment say `GitHub refused the supervisor's token (401); the merge waits until the token is replaced and the supervisor restarted` (`cmd/supervisor/stages/candidate_landing.go`). When GitHub says a pull request is open on the candidate branch but does not list it yet, the factory keeps looking. A merge GitHub refuses because the default branch was just modified is tried again up to five rounds. When GitHub permanently refuses to open the pull request (the token lacks Pull requests: write, say), the candidate is left for the Owner and the issue still closes.
- The factory's own pull request is told by its author's login, `extensions.github_app_login` (the App's bot login, as `name[bot]`); a numeric `github_app_id` never stands in for it. A pull request opened by an earlier build, before pull requests carried the run's marker, is still adopted when the factory's account opened it and its body opens by naming the run (`cmd/supervisor/stages/candidate_pull_request_open.go`). The progress comment is likewise told by its author's login. An install that names an ID but no login merges nothing, writes no progress comment and publishes no bug report: every candidate is left for the Owner and `sisf doctor` warns that the login is missing. A wrong login shows in the reason: the author is not the factory's configured account.
- The supervisor's token needs Contents: write and Pull requests: write. A protected default branch that refuses the factory's merge leaves every pull request for the Owner.
- Candidate branches are never deleted by the factory. Delete them once their pull request is merged or closed.

## Signing in

`sisf login` starts a device-style login: open the printed URL, check the code and approve. The CLI stores a short-lived token owner-only. The control URL comes from `--url`, then `$SISF_URL`, then `http://127.0.0.1:7463`; `$SISF_TOKEN` overrides the stored login. `--name` labels the token on the approval page and `--scope` (repeatable) narrows what it may do. This is how a person gets a personal access token: `POST /auth/tokens` has no page of its own in the dashboard, and a script is given the token in `$SISF_TOKEN`.

People sign in to the dashboard with the providers the control process is given (`cmd/factoryd/wiring/identity_env.go`). There is no Owner token any more: the Owner is whoever signs in as an identity listed in `SISF_OWNER_IDENTITIES`. Roles other than Owner come from the person's permission on the factory's GitHub repository (`internal/rbac`).

| Variable | Meaning |
|---|---|
| `SISF_EXTERNAL_URL` | origin people and MCP clients reach the control server at; the OAuth issuer. Defaults to `http://<listen address>` only on loopback |
| `SISF_OWNER_IDENTITIES` | comma-separated `issuer#subject` identities that hold the Owner role |
| `SISF_AUTH_OIDC_ISSUER`, `SISF_AUTH_OIDC_CLIENT_ID`, `SISF_AUTH_OIDC_CLIENT_SECRET` | OpenID Connect sign-in, offered as `google` |
| `SISF_AUTH_GITHUB_CLIENT_ID`, `SISF_AUTH_GITHUB_CLIENT_SECRET`, `SISF_AUTH_GITHUB_URL`, `SISF_AUTH_GITHUB_API_URL` | GitHub sign-in, offered as `github`; the URLs default to github.com |
| `SISF_SUPERVISOR_ADMIN_ADDR` | the supervisor's admin socket, which the emergency stop and rollback actions call |
| `SISF_DOCS_DIR` | directory `docs.list` reads; unset means none |
| `SISF_EDGE_COUNTERS_URL`, `EDGE_COUNTERS_TOKEN` | the edge's admin listener and its read-only counters token; setting the URL turns on the Decision Layer. The control process never holds `EDGE_ADMIN_TOKEN` |
| `SISF_LOCAL_STORE_DIR` | the control zone's encrypted local secret store (`local:` references); its key is made on the first start |
| `SISF_CONTROL_SECRET_<NAME>` | a secret the `env` provider serves as `env:<NAME>`; only in `secrets/control/runtime.env` |
| `SISF_TRUSTED_PROXIES` | networks the edge connects from; the address the edge forwards is believed only from these (default loopback). It names the client for the rate limits of the public bug-report route, sign-in, device login and OAuth client registration; an IPv6 client is named by its /64 |

`sisf init` writes these: the non-secret settings into `factory.yaml` and from there into the Compose file or the Standalone unit, the client secrets and `EDGE_COUNTERS_TOKEN` into `secrets/control/runtime.env` only. In the simulation profile and a `--dev` install, sign-in is the fake identity provider of `sisf sim oidc` on `127.0.0.1:7468`, which the install starts itself and which also stands in for GitHub sign-in, with the subject `owner` as the Owner; in a `--dev` install a browser must first unlock sign-in with the secret each `sisf up` writes to `secrets/control/dev-sign-in` (see [development install](install.md#development-install)). A real install must name at least one provider and one Owner; `sisf init` refuses otherwise, and refuses the fake. `sisf doctor` checks the same: a provider and an Owner are configured, the external URL is sane, the fake is used only by the simulation (and, with a loud warning, a development install), and control reads the edge's counters with its own token and holds no edge admin token.

In Docker mode control reaches the supervisor's admin socket as `unix:/run/sisf/admin/supervisor.sock` on the `supervisor-admin` volume the two share; in Standalone it is `127.0.0.1:7464`.

Sessions, tokens, step-up confirmations and OAuth grants are held in memory in this release. Restarting the control process signs everyone out and voids every token. An OAuth client an MCP client registered for itself expires an hour after registration when nobody consented to it, and 30 days after a person last consented to it (`internal/oauthas/dynamic_client_limits.go`). Each of these tables is bounded (the device-login table holds 1,024 requests). Starting a sign-in, a device login or a client registration is limited to 10 per source per minute and, per table, to a rate of random evictions that keeps a flood rotating through many sources from pushing out a person's entry (`StartLimiter` and `FloodSafeRate` in `internal/intake/report/limiter.go`: 83, 83 and 81 a minute by default). Only a start that pushes out another source's entry chosen at random counts against that rate, so busy sources that hold several entries each never hold up a new one; beyond either limit the answer is 429 with `Retry-After`, and a step-up of a person who holds a role is exempt. When a table is full, a new entry pushes out the oldest entry of the source holding the most; when every source holds one, it pushes out an unprotected entry chosen at random (a source that already holds an entry loses its own oldest entry first), so a flood from many addresses cannot lock everyone out. Step-ups of people who hold a role, login requests being approved and clients with a consent pending are protected: they are not pushed out for an unprotected entry, and a new unprotected entry is refused only when every entry left is protected, with 429 and a `Retry-After` until the first open entry lapses, without spending a random eviction. Entries also expire (a sign-in flow after 10 minutes, an unused registration after an hour); the owners are `internal/auth/login_flow.go`, `internal/control/api/device_grants.go` and `internal/oauthas/dynamic_client_limits.go`.

An action that needs step-up (deciding an approval, a rollback, a budget change) runs only from its form in the dashboard, after the person confirms their identity at the provider for that one call: the action and the approval request, approval or exact input it names. The confirmation lapses after five minutes and is spent by the one call; another call needs another confirmation. A token never carries one, and a session is not honoured for these actions over REST or by a WebMCP tool, which does not list them: those calls answer `STEP_UP_REQUIRED` and point at the dashboard. Minting a personal access token follows the same rule: the step-up names `auth.tokens.create` and the digest of the exact token (name, scopes, lifetime), and approving a `sisf login` request names `auth.device.approve` and its user code, which the verification page's form does for you. The confirmation is the control: a fresh sign-in at the provider, bound to one action and target and spent once. As defence in depth, both mints and every dashboard action form are served only to a form submitted on control's own pages (`POST /auth/tokens`, `POST /api/v1/device/approve` and `POST /actions/{name}` take form fields with `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, `Sec-Fetch-Site: same-origin` and `Sec-Fetch-User: ?1`, never a JSON body, a script's fetch or a request without those headers). That check cannot tell a person's click from a script in the page that submits the form; the step-up does. Browsers send these headers only to an https or loopback origin, so a control plane on plain http off loopback refuses these forms. There is no untargeted step-up. Every surface limits writes to 60 per minute per person. A write called with an idempotency key (`idempotency_key` in the body, the `Idempotency-Key` header, or `sisf call --idempotency-key`) runs once per person, action and key: a retry with the same input within 24 hours gets the first answer, and the same key with another input answers `CONFLICT`. The control zone keeps these records in the `control.idempotency` namespace of its store and prunes them after the retention.

## Reconciliation with GitHub

Besides webhooks, the control process asks GitHub for its repository's changed issues every `SISF_GITHUB_RECONCILE_INTERVAL` (10s to 1h, default `1m`; at most `SISF_GITHUB_RECONCILE_MAX_PAGES` pages of 100 issues, default 10) and hands any change no webhook delivered to intake through the same inbox, so a lost delivery is picked up within one interval (`sisf init --github-reconcile-interval` records the interval in `factory.yaml`, from where it reaches the control unit in both modes), while a failed or slow poll (bounded at 30s) is retried an interval later without holding back webhooks or approvals (`cmd/factoryd/wiring/control_reconcile.go`).

- Changes are read oldest first from the stored position (`control.reconcile` namespace). A poll that reaches its page bound stores what it read and the next poll continues from there, so a repository with a long history is taken in over several polls and nothing is dropped. Until the backlog is worked off, `sisf status` (`factory.status`) shows `github.backlog: true`.
- The position advances only to the last change actually stored; it moves back only to read a one-second burst again (below). If the store fails partway, the poll stops and the next one reads the failed change again. A change that fails validation does not hold up the ones after it, which are stored. The position stays before that change for up to 5 polls (`github.retrying`). After that it is given up, logged, and listed in `github.skipped`. The issue's next change is read normally.
- The factory's own comments, labels and closes are not handed back to intake. Around each edit the control zone reads the issue (`cmd/factoryd/wiring/factory_issue_edits.go`) and records the edit only when the two reads differ by nothing but what the edit did. GitHub's update times have whole-second precision, so a poll takes a change for that edit only at exactly its update time, only when every change before the edit had already been taken in, and only when its content proves it: the issue's title, body, state and labels are what the factory saw after its edit, and every comment since just before the edit carries the factory's marker (`internal/control/factory_write.go`). Anything else, a person's change in the same second included, is handed to intake, which reads the issue and finds nothing new when there is none.
- A poll steps through more changes within one second than a page holds by page number and keeps the page with its position, so a bulk edit is worked off like any backlog. When an issue of that second changes during the walk, it shifts the others, so the walk starts that second over; a restart starts it over too (`pkg/github/poller_page_walk.go`).
- Before parking an issue whose wait for an answer is over, the control zone makes sure a poll that started after the deadline read the listing to its end, and polls at once when none did (after a pause, or when an answer landed within one interval of the deadline); a failed or unfinished poll defers the parking (`cmd/factoryd/wiring/control_clarify_expiry.go`). While a parking waits, `sisf status` shows since when as `github.parking_deferred_since` and why as `github.parking_deferred_reason`.
- A parked issue resumes when a person removes `sisf:needs-info`, even without that webhook. This happens once the factory's own label was confirmed on GitHub: any later event or polled change that shows the issue without the label leads to the issue being read again, and it resumes only if the label is really gone (`internal/intake/service.go`). Every other trigger of intake (opened, edited, labeled, closed, reopened, comments) is already decided from the issue as GitHub shows it now.

## Public bug reports

The application's users send bug reports through the edge to control's public report route. Each report is stored redacted in the control zone's store (`control.reports`), so a restart loses none, and a duplicate is counted against the report already stored (`internal/control/report_store.go`).

- The route accepts 5 reports per client and 60 overall per hour (`internal/intake/report/handler.go`); a client over its limit gets 429. One client may also hold at most 10 reports waiting to be published; beyond that it gets 429 with `Retry-After` (`internal/control/report_store.go`). Report text has control characters, every default-ignorable code point and U+2800 removed before it is redacted, so a secret split by them is still found, and HTML character references in the title are decoded before they are stripped and redacted (`internal/intake/report`, `internal/control/report_issue_render.go`).
- Each report is published as a GitHub issue labelled `sisf:report` and nothing else, in the order it was received, except that a report whose last attempt went unanswered waits behind the others for 3 minutes, and up to 5 minutes after further unanswered attempts, and at most 5 a minute (`cmd/factoryd/wiring/control_report_publish.go`, `internal/control/report_publisher.go`). At most 50 report issues are opened in any rolling 24 hours (`internal/control/report_publish_budget.go`); each attempt is charged against that budget in the same write that records it, and the charge is returned when GitHub refuses the issue with a client error or rate limit. When that budget is spent, publishing pauses until the oldest counted issue is a day old and nothing is dropped, except that a report whose attempt went unanswered is still looked for and tried again on the charge that attempt holds; `sisf status` shows `github.reports_publish_paused_until` and the backlog in `github.reports_waiting`. The budget is kept in the store, so a restart does not reset it. The issue's text is made safe for GitHub and redacted again. Intake never takes such an issue up by itself; see the [security guide](security.md#limits-to-know) for what adding `sisf:ready` to one does.
- Reports are kept for 90 days after they were first received; the control pass prunes lapsed ones. The store holds at most 1,000. When it is full, a new report first evicts the oldest report GitHub refused for good; otherwise it drops the newest waiting report of the client holding the most, as long as that client holds more than one report and more than the newcomer's client, and never a report being published. `github.reports_dropped` counts the reports dropped this way. When every waiting report is from a different client, the newcomer gets 503 with a `Retry-After` until reports are published or lapse (`internal/control/report_store.go`).
- The store keeps a sender only as an HMAC-SHA256 of the client key (an IPv4 address or an IPv6 /64) under a secret made once per install and kept in the same store, and only while the report waits (`internal/control/report_store_clients.go`). That protects a leaked record or export; it does not protect against a leak of the whole store, which holds the secret too.
- If GitHub refuses one report's issue with a client error (4xx other than 401, 403, 404, 410 or 429), that refusal counts against the report and the next one is tried; after 3 refusals the report is given up. Token, permission, repository or rate-limit errors pause publishing without counting against any report. An outage (5xx) or a lost answer pauses publishing too. An attempt is cut off after 2 minutes; once it is surely over (3 minutes after it started, so no other publisher sharing the store may still be waiting for its answer) a pass looks for the issue it may have opened and, when there is none, returns its charge to the budget, as it charges the new attempt or, when that is not due yet, at once, so a report holds at most one charge; until then the reports behind it are tried. A report whose attempts keep going unanswered is never given up for that: it is tried again 3 minutes after its first unanswered attempt and then at most every 5 minutes, while the reports behind it are tried, and it stays in `github.reports_waiting` until it is published, refused, past the report retention (90 days from receipt) or pushed out of a full store.
- `sisf status` shows `github.reports_waiting`, `github.reports_failed`, `github.reports_dropped`, `github.reports_publish_paused_until` and `github.report_publish_error`. When `report_publish_error` says `PERMISSION_DENIED` about `sisf:report`, the issue was opened without its label: the factory's GitHub token needs permission to label issues.
- A report issue lost between opening and recording (a crash) is looked for by its marker among up to 1,000 recently changed issues, with the label or without it, so it is recorded rather than opened twice; it can be opened twice only when GitHub lists more than 1,000 changed since.
- An install that names the factory's account by its ID only publishes none and logs why once; set `extensions.github_app_login`.

## State and budget

`sisf state bootstrap` prepares the state store (migrations, one role per zone, the budget record). `sisf up` does this for you. The budget mode default and its confirmation are in [ADR 0007](../adr/0007-budget-default-unlimited.md); code is in `internal/budget`. `factoryd dispatcher --run-estimate-micros N` is the amount each run sets aside from the budget when it is claimed; `sisf init --budget-cap` sets it from `--run-estimate` (default a fifth of the cap), and an unlimited budget leaves it at 0. A rollback reserves through the rollback reserve that ordinary runs cannot reach and is never blocked by an exhausted budget; its nominal cost is recorded in the ledger either way (`internal/supervisor/release/rollback_budget.go`). Usage an agent reports with tokens but no cost, as the Codex CLI does, is recorded as reported, with no cost. When the run's reservation is closed, the part of it that the run's booked costs did not cover is charged as unverified (`dispatcher.CloseReservationOfRun` in `internal/dispatcher/run_spend.go`). The booked costs, and whether some usage stated none, are read from the run's rows in the ledger recorded since its reservation was made, never from the dispatcher's record of the run, which the agent zone can rewrite; a run with no row in the ledger, with no record at all (also when the control zone stops it), or with a row of negative cost, is charged its whole reservation as unverified, and one with a row that states a cost of 0, with tokens or without, the part its booked costs do not cover; a run that books any positive cost, however small, is taken at its word, since the agent zone meters itself; on PostgreSQL the database itself dates every reservation and usage row a zone role inserts by the server's clock, refuses verified usage, and refuses agent usage that does not name a reservation of its own run (migration 13; see [ADR 0007](../adr/0007-budget-default-unlimited.md) for exactly what is enforced where); the `spend.reported_cost` that `runs.inspect` shows is that record's unverified figure and decides nothing. The record can only add a charge, for an attempt that reported nothing at all. With an unlimited budget and a run estimate of 0 nothing was reserved, so that usage is not counted. `budget.get` warns when some unverified usage states no cost, with tokens or without, and its `unpriced` total counts those rows by the same rule a run's close applies (`core.Usage.CostUnreported`). When a run stops, or QA passes or holds it, the factory closes the reservation that run's claim made, found from the run's ID (`budget.RunReservationID` in `internal/budget/gate.go`); the reservation named in the agent zone's run record is not trusted. A close that fails is tried again on every QA pass until it succeeds. One that fails five times with `NOT_FOUND`, `TAMPERED` or `INVALID_ARGUMENT`, which no retry changes, is recorded as `close-abandoned/<run>` with its code and reason, reported once, and its reservation stays held until a person settles it (`cmd/supervisor/stages/run_close_due.go`).

## Decision Layer

When `SISF_EDGE_COUNTERS_URL` is set, the control process reads the edge's counters every five minutes and runs the Decision Layer (`internal/decision`) under the policy in force. A recurring regression of an endpoint's 5xx rate becomes one GitHub issue for the Owner; the layer recommends and never changes anything itself. Proposals are remembered in the operational store, so a restart does not open a second issue for the same condition.

Without a `decision.system_one` section in the approved `.sisf/factory.yaml` (the repository's copy, read at the policy commit the Owner approved, not the install's `<dir>/factory.yaml`; see [two files named factory.yaml](policy-and-approvals.md#two-files-named-factoryyaml)), the deterministic rules decide alone. With one, the layer also asks that System One backend the typed questions of `DECISIONS.md` about each proposal; its answer can only hold the proposal, make it more cautious or lower its priority, never raise it:

```yaml
decision:
  system_one:
    backend: jev            # jev or clef
    endpoint: https://system-one.example.test   # HTTPS, or HTTP on loopback
    version: "1"            # an explicit protocol version, never "latest"
    timeout: 30s            # above zero, at most 2m
    credential: env:SYSTEM_ONE_KEY  # optional secret reference ("env:NAME" or "local:path/name"), never a value
    model:
      provider: jev
      model: jev-1          # judgments reporting another route are refused
```

The schema is `schemas/factory.schema.json`; the checks are in `pkg/manifest/decision_system_one.go`. The adapter refuses redirects, so a request and its credential only ever reach the configured endpoint.

## Secrets of the control zone

The control process opens two secret providers, and no other zone opens any (`cmd/factoryd/wiring/control_secret_providers.go`). `secrets.list_refs` lists their references, never values; a System One credential resolves through them.

- `env:NAME` reads `SISF_CONTROL_SECRET_NAME` from the control zone's env file, `secrets/control/runtime.env`. Add the line there and restart; the variable is refused in every other zone's file, and nothing else in the environment is reachable through a reference.
- `local:path/name` reads the encrypted store in `SISF_LOCAL_STORE_DIR` (`/var/lib/sisf/control/secrets` in the `control-data` volume, `<dir>/data/control/secrets` in Standalone). The store has no writing command yet, so use `env:` references for now. The `local:` references `sisf init` writes into `<dir>/factory.yaml`, each component's `credentials_ref` such as `local:control/credentials`, are a different thing: they name files below `<dir>/secrets` that the installer creates and checks (`internal/install/layout.go`), not entries of this store.

## Agents and builds

Real coding and QA agents run only in Standalone mode under `trusted_code_only`; the flags and the refusal of `--agent-home` and `--qa-home` near the factory's protected paths are in [installing](install.md#real-agents-in-standalone). With `--exec local` candidate builds are held: the supervisor refuses to build an agent's code with the local backend. A Standalone install builds in a Docker sandbox the operator provides (`--exec docker` with the runner filter, sandbox network, egress proxy, runner image and a QA launcher); see [installing](install.md#building-in-a-docker-sandbox). What the runner filter lets through, and so refuses, is listed in `internal/dockerfilter/doc.go`.

In Docker mode `sisf doctor` and `sisf up` refuse a Compose file that holds more than one YAML document, carries a YAML tag outside the core schema (such as `!reset` or `!override`), or names a volume or network other than `<project>-<key>` (`internal/install/isolation_compose.go`).

## Edge tokens

The edge (`cmd/edge`) reads two tokens from its environment. `EDGE_ADMIN_TOKEN` guards its admin listener (`--admin-listen`) and can change the traffic split; only the release supervisor holds it. `EDGE_COUNTERS_TOKEN`, which `sisf init` writes for the edge and the control process alike, authorizes `GET /counters` and nothing else; every other request with it is refused with 403. The two must differ, or the edge refuses to start. The control process reads the counters with `EDGE_COUNTERS_TOKEN` through a client that has no way to change the split (`internal/edge/admin_client.go`).

## A held release

A release the supervisor holds waits in ReleaseCandidate. One it refuses before anything is deployed blocks its issue with cause `release_refused` and the refusal's code, and the Owner's retry returns it to Ready for a new run ([Why is my issue stuck?](stuck-issues.md#causes-of-a-block)). A refused candidate is never released. Its pull request stays open for the Owner, marked `refused`. A governance change is published only in a governance update a person makes. The trusted control surface is `DefaultProtectedPaths` in `internal/supervisor/release/governance.go`: every Go package the supervisor, the command line (`./cmd/sisf`) or the control unit (`./cmd/factoryd`) links (generated from `go list -deps`, with a test that fails when the list is stale), which includes identity and access code and the whole of `ui/`, plus the edge (`cmd/edge`, `build/edge.Dockerfile`) and `go.mod` and `go.sum`, which are named by hand. A candidate the factory publishes by itself may change only the inputs of the unit it releases: built in, only the application's linked package directories for `app` (never `go.mod`, `go.sum` or `go.work*`), and nothing for `control`, or what the Owner declared in `release.unit_inputs` ([installing](install.md#declare-the-inputs-of-the-application)). Any other path, such as documentation, tests, `go.mod`, a Dockerfile, the Makefile or the dashboard, is refused for the Owner's approval, at release and again before the merge (`internal/supervisor/release/unit_inputs.go`, `cmd/supervisor/stages/candidate_landing.go`); the protected paths stay a second refusal layer, and such a pull request stays open for the Owner. The paths are listed from GitHub's comparison of the policy commit with the candidate when the candidate is released and again before the merge; a listing GitHub cuts short is refused, and one GitHub cannot give now is waited for (`cmd/supervisor/stages/changed_paths_from_github.go`). A path that is not spelled in its own clean form is refused. A candidate whose program is identical to the serving one is refused with `ALREADY_EXISTS`, since there is nothing to deploy or judge; the Owner reviews and merges its pull request by hand. The decision is [ADR 0023](../adr/0023-every-release-ends-in-a-state-the-owner-can-act-on.md), which is still proposed.

A held release is not tried again by itself: nothing was deployed. It shows in four places.

- The supervisor logs it once, at warning level: `release held before anything was deployed: the issue waits in ReleaseCandidate for the Owner's retry`, with the issue, `result`, `state`, `cause`, `code`, `reason` and `release` (`cmd/supervisor/lifecycle_loop.go`, which also holds the lines for a refused or undone release).
- `sisf runs explain <issue>` answers stopped with cause `release_held`, the supervisor's reason as `release_hold` evidence (shown to the Owner only), and the way out. `sisf runs inspect <issue>` shows `release_hold`.
- The issue's progress comment adds a **Release waiting:** line. It is chosen by the result and the code only and never carries the reason (`cmd/supervisor/handoff/release_hold.go`).
- The record is `release-hold/<run>/<attempt>` in the supervisor's `build` namespace.

The usual cause is `RELEASE_HOLD` with "real traffic is too low to judge the release and the application has no synthetic suite". A release with fewer real requests than `release.rollback.min_samples` in a window is judged by the application's synthetic suite for at least `release.low_traffic.min_hold`. The supervisor runs the suite only when it is given `--synthetic-program`, and refuses to start when that program is missing, not a regular file or not executable (`cmd/supervisor/synthetic_program.go`). Before a low-traffic release deploys anything, the supervisor asks the suite whether it can run, and holds the release when it cannot. A Standalone install builds `bin/hello-app-synthetic` and passes it when the manifest names `release.low_traffic.synthetic_suite`. A Docker install has no synthetic suite yet, so a release there with too little traffic holds; once real traffic reaches the minimum, the Owner's retry lets it start over.

The way out: remove the cause (send traffic, give the supervisor its synthetic suite, lift the emergency stop), then run `factoryd issue retry --issue owner/repo#N` on the factory's host, as the Owner, with the control zone's environment. The supervisor releases the candidate again on its next round, and the hold is cleared once that release goes ahead. A retry by anyone else is denied, and a second retry before the new release ends answers `CONFLICT`.

## A release that was not watched to its end

A release whose rollout started and that no supervisor watches, for example after a restart, is restored to the last known good release at startup and on every pass, then blocked with cause `release_interrupted` (`internal/supervisor/release/release_recovery.go`). The same happens when an emergency stop takes effect during the rollout, when traffic cannot be moved to the release, or when a verified release cannot be recorded (`internal/supervisor/release/rollout_and_watch.go`, `verify_publish_and_close.go`). One that could not be observed, measured or synthetically checked is blocked as `release_unjudged`. A release the rollback rules judged unhealthy is blocked as `rolled_back`. Each of these writes a recovery report and is retried by the Owner like a refused release. A restored release might have been healthy; its summary says that nothing is known about its health.

A verified release is recorded as the last known good release only while the running system serves it, healthy (`internal/supervisor/release/verified_release_lkg.go`). One a later release superseded is closed unpublished, and its pull request is left for the Owner unless it was merged already. One that no longer serves or turned unhealthy, and was not superseded, is switched back to the last known good release when there is one, and its issue is blocked with cause `release_unjudged` (lifecycle step Verified to Blocked); its pull request stays open and unmerged, and the Owner's retry returns the issue to Ready. A deploy backend that does not answer is an outage the release waits on in Verified, not a block. When a verified release is finished, its QA receipt and delegated keys are judged as of its Verified step, so one that expired since does not hold it. The audit log records `release.rollback` (with `without_lease=true` when the switch was made without the issue lease), `release.verify_recovered` (a release left in Monitoring that was already the last known good release, verified from the running system) and `release.unjudged`.

An emergency stop freezes forward steps only. The supervisor still rolls back a release in Canary or Monitoring while a stop is in force, also when another holder keeps the issue's lease; the blocks are written by the first pass that can take the lease. Verifying a release that is already recorded as the last known good waits until the stop is lifted. A release held after it was verified is not left: a later pass finishes it (publishing, merging the pull request, closing) once the stop is lifted or the outage it names is over, and the progress comment says what it waits on. Do not close such an issue by hand ([Why is my issue stuck?](stuck-issues.md), [ADR 0023](../adr/0023-every-release-ends-in-a-state-the-owner-can-act-on.md)).

In Standalone the supervisor records the application process of each slot under `<dir>/data/trust/local-slots/` (`adapters/deploy/local/slot_records.go`). At start the deploy backend finds the processes an earlier supervisor left again, verified by pid and start time (on Linux read from `/proc`, which a step of the clock does not change), and serves from them, so a verified release that still runs is judged from the running system before the last known good release is adopted. No process is matched by name or port. A found process whose record names another port than its slot has now is stopped and its record dropped. A found process is stopped when a release is staged over its slot and when the supervisor stops; one that ignores `SIGTERM` is killed after five seconds. Its critical log lines are not counted, and it may exit on its next write to its standard error, since the supervisor that read that stream is gone. A slot record whose process cannot be asked about, because its start time cannot be read (from `/proc` on Linux, from `ps` elsewhere), makes the supervisor refuse to start with `UNAVAILABLE` rather than drop the record: fix what fails, or, after checking that the recorded process is gone, remove the record file under `local-slots/`. A stop that cannot confirm by its deadline that the pid still names the recorded process gives up with an error and sends no kill.

A verified release the probe does not see serving (no answer, or an answer that names nothing) is waited for for two observation windows, twenty minutes by default (`internal/supervisor/release/verified_release_unseen.go`), before it is restored to the last known good release and blocked. The wait starts again whenever a pass sees the release serving, healthy, and on every pass an emergency stop skips; at startup the supervisor waits the same time for it before adopting the last known good release, once for all such releases together. Verified releases are ordered by a sequence the store numbers, never by the clock, except two releases an earlier build verified before steps were numbered, which are ordered by when their steps were written.

## A second release of a unit

The factory releases one issue of a unit after another without the Owner. After the supervisor merged a verified release, it moves the commit later candidates are built on to the merge commit, and only on proof that the merge holds what QA judged and nothing else: the merge contains both the commit it was built on and the candidate, GitHub's comparison of the two lists no foundation file, ADR or protected path, the merge's first parent is the approved revision or a merge the supervisor already followed, every path the merge changes over that parent holds what the candidate holds, and the foundation files at the merge have the digest the Owner approved ([ADR 0026](../adr/0026-the-commit-to-build-on-follows-main.md), `internal/policy/build_base.go`). The policy in force does not move, so approvals and runs under way stay valid. The commit is kept in `control.policy/build-base`, which only the control zone can write.

When the proof fails, for example because someone pushed a commit to main, or the Owner squash-merged the release's pull request, the factory stops building on main: the release's issue says so and names the reason, and every new issue is refused with `APPROVAL_REQUIRED` before a run starts. Before every merge the supervisor also checks main: when main changes a foundation file, an ADR or another protected path since the commit it builds on, for example `AGENTS.md`, it does not merge, leaves the release's pull request open for the Owner with the reason and stops. While stopped, a run under way ends at its next stage: at build as `policy_superseded`, at release as `release_refused` with reason `base_not_accepted`. Merge or close the pull request the factory left open first. To resume, review what changed on main and put a policy revision in force that contains it ([Changing the policy](policy-and-approvals.md#changing-the-policy)); the stop ends with that approval. Issues that were Ready under the earlier policy are then blocked as `policy_superseded`; retry them.

A candidate whose base does not contain the commit of its unit's last known good release is held right after its build, before QA, with reason `base_lacks_release` and the same text the release refusal gives, and its issue is blocked for the Owner. This also happens when a second issue of a unit was coded while the release before it was still under way: retry it, and it is coded on the commit the supervisor follows to then; the release step refuses it again with `APPROVAL_REQUIRED` should one ever get that far (`internal/supervisor/release/base_contains_lkg.go`). Building on such a base would publish a release without the one serving now. A first release on a fresh install, whose last known good release comes from the manifest, and a release whose last known good release is the base itself are not affected. When GitHub cannot compare the two commits now, or the last known good release cannot be read now, the release waits; an entry of the last known good release the supervisor did not write holds it for the Owner.

The check follows ancestry, not content: the base contains the commit only when that commit is one of its ancestors. If the Owner squash-merges or rebases the pull request of the release that became the last known good release, or closes it unmerged, main never contains that commit: the supervisor stops building on main, and a candidate built on main's head is held before QA. The way out is a merge commit on main whose parents include the commit the hold names, for example `git fetch origin <commit>` (or `git fetch origin pull/<number>/head` once the branch is gone), then `git merge --no-ff <commit>` on main and push. After a squash merge this merge brings in no new content, only the ancestry. Put the policy in force on that merge commit ([Changing the policy](policy-and-approvals.md#changing-the-policy)), then retry the issue: GitHub's comparison of that commit with the last known good release's commit then lists nothing, so the check passes (`pkg/github/client_git_data_test.go`).
