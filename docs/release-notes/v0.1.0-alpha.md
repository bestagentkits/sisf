# SISF v0.1.0-alpha

Release date: unreleased.

End-to-end evidence: to be added before publishing.

This is the first alpha of SISF, a self-improving software factory in one deployment: it takes in GitHub issues, has an agent write a change, has an independent QA agent judge it, releases it behind a trusted supervisor with automatic rollback, and merges it once the released version is verified. It is for evaluation on a machine you control, not for unattended production use. What each test proves is in the [acceptance matrix](../acceptance-matrix.md).

## What the alpha contains

- Two operating modes: Standalone (local processes, trusted code only) and Docker Compose. Every other backend is unsupported or experimental ([capability matrix](../capability-matrix.md)).
- The `sisf` command line: `init`, `up`, `stop`, `restart`, `down`, `doctor`, `status`, `runs explain`, `call`, `emergency-stop` and the rest ([CLI reference](../guides/cli-reference.md)), and the Owner's host commands `factoryd policy approve`, `factoryd policy request` and `factoryd issue retry`.
- The three-zone conformance checker, signed Owner approvals, the hash-chained audit log, the dispatcher with fencing, independent QA with hard gates, the release supervisor with automatic rollback and the emergency stop.
- Sign-in through OpenID Connect or GitHub, with the Owner named at `sisf init`; one action service behind REST, the CLI, remote MCP, WebMCP and the dashboard; the Decision Layer; budget modes.
- In Standalone with a Docker build sandbox, a release runs the candidate's own program ([ADR 0022](../adr/0022-standalone-deploys-the-candidates-own-program.md), proposed).
- Every release ends in a state the Owner can act on: a refused release blocks its issue with cause `release_refused`, a release no supervisor watched to its end is restored and blocked as `release_interrupted`, one that could not be judged, or a verified release that no longer serves its unit healthy and that no later release superseded, as `release_unjudged`, and the Owner's retry returns each to Ready ([ADR 0023](../adr/0023-every-release-ends-in-a-state-the-owner-can-act-on.md), proposed; [Why is my issue stuck?](../guides/stuck-issues.md#causes-of-a-block)).
- Public bug reports are stored in the control zone and published as GitHub issues labelled `sisf:report` for a person to triage, in receipt order and at most 50 issues in any 24 hours, with nothing dropped when that budget is spent ([operations](../guides/operations.md#public-bug-reports)).

## Install prerequisites

- Linux or macOS. `sisf` does not build on Windows.
- Go 1.25, git and GNU Make, and a checkout of this repository: `sisf up` builds the factory from it every time it starts. Install the command line with `make install`.
- Docker with Compose, for Docker mode or for a Standalone build sandbox.
- Ports 7460-7469 free on 127.0.0.1; one factory per machine.
- An install directory on a file system that supports `flock`.
- For a development install, a GitHub CLI login with write access to the repository; for a real install, a GitHub App installation, a long-lived token, an OpenID Connect or GitHub sign-in provider and an HTTPS origin ([installing a factory](../guides/install.md)).

## Known limitations

- Proven so far without a paid model only: two release rehearsals against a sandbox repository, run once each on darwin/arm64 with a scripted coder and a fake QA judge. A paid run with real Claude and Codex agents has not passed end to end on this release, and the Standalone program export has not been run on any other platform.
- A real GitHub App, real Google sign-in and real MCP clients are tested only against fakes.
- The GitHub token is read once per start and never refreshed. A GitHub App installation token expires after an hour, so a real install cannot run unattended for long; replace the token and restart ([installing](../guides/install.md#1-github-an-app-and-the-token-the-factory-acts-as)).
- Standalone runs trusted code only. Agents run unconfined as your operating-system user, and a candidate that passed QA is released as a host process of that user. With `--exec local` candidate builds are held.
- A Standalone unit must be one program, built for the supervisor's operating system and architecture; a unit that needs more than one file to run cannot be released this way. The program store is on the trust volume, which the agent's user can write in Standalone: a changed file is refused before it is started, but that user can still stop or replace the running process ([ADR 0022](../adr/0022-standalone-deploys-the-candidates-own-program.md)).
- Docker mode has no container sandboxing for untrusted code, no synthetic suite (a release with too little real traffic holds until the Owner retries it), and no tested host route to check or lift an emergency stop.
- Sessions, tokens, step-up confirmations and OAuth grants are held in memory; restarting the control process signs everyone out.
- Putting a policy in force and retrying a Blocked issue run only through `factoryd` on the factory's host. There is no starter template for the policy files.
- Control and the supervisor share one GitHub token, so the rule that only the supervisor merges is enforced in code, not by the credential.
- On PostgreSQL the lease trigger stops a zone role from forging a lease token, but not from taking over a live lease, because the database does not judge expiry. Two supervisor processes of one factory can both roll back an interrupted release; run one supervisor per factory.
- After a unit was killed rather than stopped, an agent CLI it started can outlive it without holding the run lock, so `sisf down -v` may delete a workspace under it; after a crash check that no agent process remains ([operations](../guides/operations.md#lifecycle)). On Linux the units of a killed `sisf up` are told to stop; elsewhere they keep running until `sisf stop`.
- A flood that spends the report route's global hourly limit makes genuine reports get 429, and about 1,000 distinct sources can fill the report store ([threat model](../threat-model.md#public-input-that-reaches-github-tm-01-tm-13)).
- A budget reservation whose close can never succeed is abandoned and stays held until a person settles it.
- No upgrade, backup or restore command exists; the [maintenance guide](../guides/maintenance.md) has the manual procedures.

## Upgrade notes

- `sisf up` applies schema migrations 7 to 10 to an existing state store. Each is backward compatible; there are no down migrations, so keep a backup to go back ([maintenance](../guides/maintenance.md#upgrade)).
- A factory started by an older `sisf` names no root key in its health answer, and the CLI refuses to send it a token until it is restarted with `sisf up`.
- A Standalone `sisf up` now holds a lock on `<dir>/run/sisf.lock` for as long as it runs, and passes it to every unit, so the install counts as running while any unit lives, also after `sisf up` was killed. `sisf stop` and `sisf down` stop such units; `sisf up` and `sisf restart` refuse until then ([operations](../guides/operations.md#lifecycle)). The install directory must be on a file system that supports `flock`. A factory still running from an older `sisf` holds no such lock; stop it before starting the new one, or the new `sisf` refuses with `CONFLICT` and names its process.
- An issue parked by a build before v0.1.0-alpha whose `sisf:needs-info` label was already removed stays parked until someone adds and removes the label again.
- The manifest `sisf init` writes lets the factory publish only the `app` unit by itself (`release.units`). A candidate that builds another unit is refused and its issue blocked.
- Self-publishing is default-deny: a candidate the factory publishes by itself may change only the inputs of the unit it releases, and any other path (documentation, tests, `go.mod`, a Dockerfile, the Makefile, the dashboard) is refused for the Owner's approval, at release and again before the merge. An application not laid out like `examples/hello-app/` must declare its inputs in `release.unit_inputs` of the installed `factory.yaml`, or every candidate of it is refused ([installing](../guides/install.md#declare-the-inputs-of-the-application)).

## Security notes

- The edge (`cmd/edge`, `build/edge.Dockerfile`) and `go.mod` and `go.sum` are protected by hand as well as the packages the supervisor, the command line and the control unit link.
- After the factory merged a release of a unit, the next release of that unit is refused until the Owner puts a policy that contains the merged release in force ([a second release of a unit](../guides/operations.md#a-second-release-of-a-unit)).
- The trusted control surface a candidate may not change now also covers `pkg/state/`, `internal/install/`, `cmd/sisf/`, `.github/`, the application's synthetic suite, `internal/supplychain/`, `internal/redact/`, `build/runner.Dockerfile` and `build/qa-runner.Dockerfile` ([threat model](../threat-model.md)).
- On PostgreSQL, triggers hold each zone role to its own lifecycle steps and to the lease API's writes (migrations 7, 9 and 10).
- The CLI sends a token or a login only to a server that names this install's factory id and root key.
- A budget reservation is closed by an ID derived from its run; the reservation named in the agent zone's run record is not trusted.
- Bug report text is unverified public input, published redacted and defused under the factory's account. Labelling a report issue `sisf:ready` makes it a request from someone without write access, so it waits for the Owner.
- In Standalone the local backend's slot records live on the trust volume, which the agent's user can write; a record is honoured only for a live process whose start time matches.
- Every Go package the supervisor, the command line or the control unit links, identity and access code (`internal/auth`, `internal/rbac`, `internal/oauthas`, `pkg/identity`) and the dashboard's templates and scripts included, the edge and `go.mod` and `go.sum` are part of the trusted control surface; a candidate that changes any of them needs a person. A candidate whose program is identical to the serving one is blocked as refused, and its pull request is merged by hand.
- Starting a sign-in, device login or client registration is limited to 10 per source per minute and, per table, to a global rate; beyond either the answer is 429 with `Retry-After`, and a role holder's step-up is exempt.
- A full sign-in, device-login or OAuth client table drops a random unprotected entry when every source holds one, so a flood from many addresses cannot lock everyone out; step-ups of people who hold a role and login requests being approved are not dropped for an unprotected entry.
- Report text has control characters, default-ignorable code points and U+2800 removed before redaction, and HTML character references in its title are decoded first. One client holds at most 10 waiting reports, and each attempt to open an issue is charged against the daily budget in the write that records it. The report store keeps a sender only as a keyed hash, which protects a leaked record or export but not a leak of the whole store.
- An emergency stop never holds a rollback, and a rollback never waits for the issue lease.
- Report vulnerabilities privately as described in the [security policy](../SECURITY.md).
